# GPU Scheduler: Milestones

Oct 23, 2026 · @Paul Collins

## How to use this plan

Eight milestones take the scheduler from types and tests to a fully event-driven system, and each one leaves something working and verifiable. This plan accompanies the architecture design doc, which defines the components, crates, and safety invariants referenced here.

Sequencing principles:

- **Pure core first.** Decision logic is built and tested against recorded and synthetic snapshots before any I/O exists.
- **Shadow before control.** The scheduler observes real demand and logs what it would do before it is allowed to act.
- **One new risk per milestone.** Each milestone introduces one new kind of external interaction, so failures are easy to place.
- **Polling before events.** Each source works with periodic resync first; webhooks are layered on afterward without changing the core.
- **Safety invariants are tested in every milestone** that touches the sequencer or an actuator.

Each milestone below states its goal, what is in and out of scope, and the exit criteria that mark it done. Detailed task planning is left to the implementer.

## Milestone details

### M0: Foundations

**Goal:** a workspace whose shared types and configuration can describe the whole system, with a test harness ready for the core.

- **In scope:** crate skeletons per the design doc; shared types for resources, models, workload classes, observations, snapshots, intents, steps, and leases; the configuration schema with loading and validation; a fixture format for recorded and synthetic snapshots.
- **Out of scope:** any decision logic, I/O, Restate, or Kubernetes interaction.
- **Exit criteria:** a config describing every current workload loads and validates; invalid configs (dangling references, inconsistent policy values) are rejected with clear errors; snapshot fixtures can be loaded in tests.

### M1: Decision core

**Goal:** a deterministic planner and sequencer that make correct, safe decisions on paper.

- **In scope:** the first-in-first-out, exhaustive-with-bounds policy strategy; minimum dwell, maximum dwell, and idle grace; readiness-based precedence; resource state machines for the GPU node and the NFS share, including manual leases, release, reclaim, and manual LLM leases; every safety invariant enforced in the sequencer; table-driven and replay tests.
- **Out of scope:** observers, actuators, persistence, and preemption of in-flight work.
- **Exit criteria:** scenario tests cover interleaved OCR and transcription arrivals, OCR followed by LLM tagging, starvation bounds, flapping prevention, and stale-observation holds; every safety invariant has at least one test that would fail if it were violated.

### M2: Shadow mode

**Goal:** the scheduler runs in the cluster, observes real demand, and logs what it would do, without acting.

- **In scope:** the Restate-hosted scheduler with its tick and periodic backstop; the observation cache with ages; a Kubernetes watch observer for model pods and node readiness; a generic HTTP/JSON adapter configured for paperless-ngx and speakr's v1 API, counting speakr's queued and in-flight work as demand (failed-with-connection-error transcriptions were NOT observable in M2; superseded in M3, where they are detected from the list and re-queued automatically: see *Plan changes* below); logs and metrics of each decision and its reason.
- **Out of scope:** the KEDA scaler, power, leases, and webhooks.
- **Exit criteria:** over at least a week of real use, the logged decisions match what a person would have chosen, and any disagreements are resolved by policy or config changes rather than code in the core.

### M3: GPU control

**Goal:** the scheduler, not each service, decides which model runs on cuda-central.

- **In scope:** the KEDA external scaler serving the allowed set; ScaledObjects for paperless and speakr workloads pointed at it; short KEDA polling and cooldown so hysteresis lives in the scheduler; manual power only.
- **Out of scope as planned:** NFS, backup, interactive sessions, and immich. What M3 actually delivered differs (see *Scope reset during M3* and the internal work packages P1 to P7 there): it also pulled in the immich demand source (and ScaledObjects for the GPU immich ML replica), speakr's failed-transcription detection and automatic re-queue, a TCP-probe reachability source for basestar (with the Prometheus observer as a spare), host-readiness gate classes (so NFS-dependent consumers can be gated), manual model leases and the durable Restate-backed core. Power actuation, backup, interactive sessions and the scheduled-jobs work stayed out.
- **Exit criteria:** with cuda-central powered on, mixed paperless and speakr workloads drain in the expected order; no two models ever run at once (the scheduler publishes at most one, and Kubernetes enforces it: see *Decided during M3*, scope reset); speakr transcriptions that fail while whisperX is unloaded show up as demand and bring it in; a scheduler restart mid-switch resumes safely.

### M4: Scheduled jobs and power

(Rescoped during M3; the previous scope was "Leases, NFS, and backup", see *Scope reset during M3*.)

**Goal:** flowmanager owns the schedules of Kubernetes Jobs, such as the backup, together with the shared resources they need, and owns the power of basestar (NFS) and cuda-central instead of a person or `power.py`.

- **In scope:**
  - *Scheduled jobs.* flowmanager owns the schedules of arbitrary Kubernetes Jobs (for example "doing a backup"). A job declares what it needs: NFS now, possibly a GPU mode later. The existing backup CronJob's `jobTemplate` is the template; that CronJob is `suspend: true`, so flowmanager creates the Jobs (marked `invoked-by: flowmanager`) and the CronJob controller does not. Backup jobs run in parallel. Verification happens in the Jobs' init-containers. On failure flowmanager raises an alert and releases what it held.
  - *Power.* flowmanager owns the NFS and GPU power transitions (`power.control: managed`), reproducing the user's `power.py` `low` state (NFS up, GPU down). It gates NFS dependents: they are scaled to zero while basestar is off. Before shutting basestar down it checks that no pod mounts NFS, and it does the same bounded drain before a GPU shutdown. A manual NFS lease brings up basestar **and** the consumers, so that their queues become visible; a GPU lease (a manual model lease on a host that is off) enables scheduling.
  - The lease manager for NFS holds (reference counts), with the power actuator workflows for basestar and cuda-central, power-off confirmed by the SSH shutdown signal and then unreachability checks, and a minimal API for manual power-on, release and cuda-central reclaim.
- **Out of scope:** the `idle` group of `power.py` (ignored for now); demand-driven power; webhooks; interactive leases.
- **Decided by the user (Oct 27, 2026):**
  - *Missed-run and retry policy is configurable per job:* a retry count (0 means no retry) and a catch-up setting for runs missed while flowmanager or the cluster was down or the job's needs never came up. Backups use catch-up (run once, late, only if the next scheduled time has not arrived). Overlap stays "at most one instance per job; skip and alert".
  - *Server definitions live in the scheduler config.* The labelled-ConfigMap discovery convention in `kubernetes-requirements.md` is deprecated; flowmanager becomes the manager of those hosts.
  - *`PoweringOn` and `ShuttingDown` get timeouts that alert and stop.* On expiry flowmanager raises an alert and enters a visible failed state; it never retries a power action by itself (a host that does not come up or go down is beyond flowmanager's scope, and an automatic retry risks flapping).
  - *Hardware:* power-on is Wake-on-LAN sent through the OPNsense router (flowmanager runs in the cluster, not on the LAN); shutdown is over SSH with russh to a forced-command key. The legacy root crate (`src/opnsense.rs`, `src/power.rs`) implemented both and was the reference; it was removed after M6 and is in git history at commit `1de46ca`.
  - *Job template:* a Kubernetes Job has no "template that is only invoked manually" kind, so the suspended CronJob stays as the template holder (approved by the user: flowmanager invokes the job, it does not store or maintain the definition). flowmanager creates each Job from the CronJob's `jobTemplate`, the way `kubectl create job --from=cronjob/...` does, and marks it `invoked-by: flowmanager`. The user will annotate the CronJob in the manifests to make clear that flowmanager is the invoker.
- **Open questions:** none remaining for design; details are settled in the build.
- **Exit criteria (built and reviewed in the replay and fake-context harness, Oct 27, 2026; not yet run against a real cluster):** basestar never powers down while a lease is held or a pod mounts NFS; a scheduled job starts at its time with its needs held and releases them when it finishes or fails; parallel backup jobs complete without disrupting paperless work; a failed job raises an alert and releases; a manual NFS lease brings up basestar and its consumers; a GPU shutdown drains with a bound; the `low` state can be reproduced.

### M5: Event-driven observation (webhooks)

**Decided by the user (Oct 27, 2026).** The question was a *webhook reporting state* (notify-then-fetch: an observer is told to re-read a source) versus a *workflow acting on that* (a webhook that triggers work). Reporting only; acting is deferred until there is a concrete use case.

- **Shape:** an inbound endpoint whose only meaning is "go poll now". The payload is ignored. The path from a source's `webhook: { path: ... }` maps to the sources that declared it. The poll result enters the existing pipeline unchanged (`Report` channel, cache, tick), so no decision logic changes. `resync` stays as the safety net: a dropped webhook costs only the wait until the next poll.
- **Separate listener** from the Home Assistant toggle listener (its own flag, port and policy).
- **Authentication is configurable and has no default.** `mesh`: flowmanager does no authentication and Istio (STRICT mTLS plus an `AuthorizationPolicy` on caller principals) mediates; `token`: a bearer token from a file, for senders outside the mesh. Nothing is external today; `token` is there for a possible use. flowmanager will run with an Istio sidecar. Home Assistant is the exception (`hostNetwork`, no sidecar), so the toggle port and the webhook port need different Istio policies.
- **Nudges are coalesced and rate-limited** per source, so a flood costs at most one poll per minimum interval. `http_json` is the only observer that is nudged; `tcp_probe` and the other pollers are out of scope. The nudge registry must survive an observer restart on a config reload.
- **Built (Oct 27, 2026; reviewed, ACCEPT WITH RESIDUAL RISKS; not run against a real cluster or a real sender):** the typed `webhook: { path }` setting (validated at load), a `Nudges` registry in `sched-observe` that outlives observer restarts and a `poll_loop` for `http_json` that polls at `resync` and when nudged (at least `--webhook-min-interval`, default 10s, between polls of a source; nudges merged), the toggle listener's HTTP plumbing moved into a shared `listener` module, and the `webhook` listener in `sched-service` (`--webhook-listen`, `--webhook-auth mesh|token` with no default, `--webhook-token-file`, `--webhook-min-interval`; 404 for unknown paths, 64 KiB body cap, auth before the body in `token` mode; `sched_webhook_requests_total{outcome}`, `sched_webhook_nudges_total`, `event="webhook"` log). The `SourceKind::Webhook` kind is unused and left as it was. Manifests for Istio and the paperless-ngx and speakr setup are documented in `docs/kubernetes_setup.md` and marked there as not tested.
- The previous scope, kept for reference: a generic webhook receiver using notify-then-fetch; paperless-ngx workflow webhooks (including paperless-gpt's tag edits) and speakr webhooks; resync intervals lengthened for sources with webhooks; metrics for event-to-decision latency; exit criteria "a new paperless document leads to a decision within seconds; dropping a webhook still leads to a correct decision at the next resync".

### M6: Manual leases from Home Assistant

(Shrunk during M3; the previous scope was "Interactive sessions".)

**Goal:** a person can hold the LLM (or a host) from Home Assistant without manually juggling models. Open WebUI itself is not integrated.

- **In scope:** a client (Home Assistant, through the toggle listener; Open WebUI is not integrated) acquires and holds a **manual model lease** through the existing handlers (`acquire_model_lease`, `release_lease`, `leases`) and the **release is manual** (a person releases it); the lease cuts batch work short with its timeout, as a reclaim does.
- **Out of scope:** interactive leases with renewal and expiry, a request path for clients to renew, priority over batch work at job boundaries for ordinary interactive requests, a model-routing proxy, demand-driven power.
- **Decided by the user (Oct 27, 2026), which changes the trigger route above:** the toggle is **Home Assistant**, not Open WebUI. Home Assistant runs inside the cluster with `hostNetwork: true` (mDNS on the 192.168.2.x network).
  - *API:* a small dedicated HTTP listener in flowmanager (its own address, like the metrics and KEDA listeners) that Home Assistant's REST switch can use: plain `GET` for state, `POST` for on and off, idempotent by name so Home Assistant never needs a lease id. A bearer token (read from a secret file) is mandatory.
  - *Scope:* manual **model leases** (one toggle per configured model; **on means a lease is held**, not that the model is loaded) **and host controls** (the manual host lease of a shared host such as NFS, which an exclusive GPU host does not take, plus `resume` for a failed power phase; `reclaim`/`unreclaim` are included too, a user decision of Oct 27, 2026: an exclusive resource with a power section, such as the GPU host, "this GPU is mine"). The read side reports held or not held plus a richer status (waiting for the host, draining batch work, model active) for a sensor.
  - *Acquire:* explicit action only, never automatic. *Release:* manual; the safety net is visibility only (a lease-age metric and an example alert), no automatic expiry.
  - *Host controls follow adoption and drain (user decision, M4 host power).* A host found running reads `on` on its host switch (it is held by an adopted `ManualHost` lease), and switching it off releases it. `POST /v1/resources/{resource}/off` and an `OFF` body release with a graceful drain, and the new `POST /v1/resources/{resource}/off-now` with an immediate one. `POST /v1/resources/{resource}/release` releases the lease plainly, with no drain. No listener config was needed (the choice is the URL, so a second Home Assistant `rest_command` or script carries the immediate variant). The host state answer carries `drain` while one is under way, and the switch-off works with no lease held (a host held up only by queued work), answering `state: "draining"` rather than `off`.
- **Exit criteria:** a manual LLM lease preempts batch work within its timeout and holds the LLM until released; releasing it lets batch draining resume. Through the HTTP listener, a request without the token is refused; on and off are idempotent; the state read agrees with `leases`, and its richer status is derived from the last tick (a model lease on a reclaimed resource reads `reclaimed`, a status that cannot be said is left out); a host toggle brings a managed host up (or waits under `control: manual`) and releases it again.

### M7: Remaining immich and preemption items

(Shrunk during M3; the previous scope was "immich and preemption capabilities", most of which M3 delivered.)

M3 already delivered the immich demand source, ScaledObjects for the GPU immich ML replica (`model: immich-ml`, low priority beside the always-on CPU replica), per-class preemptibility with recovery actions (re-queueing failed speakr transcriptions) and early switching for classes that declare it safe (with a bounded wind-down). What may remain, to be re-confirmed with the user before anything starts: validating immich's alpha queue API under a real import; consumer-side actuators (pausing intake and stopping work directly, since today the work ends only because the model is withdrawn); re-queueing interrupted speakr summaries; tightening the speakr demand counts. If none is wanted, M7 is dropped.

**Decided by the user (Oct 27, 2026): M7 is dropped as a milestone.** Its four items become a backlog, each picked up only when real running (logs, metrics) shows the problem:

- *Validate immich's queue API under a real import:* a smoke test at first deployment, not a build. The deployed immich is **v3.3.3** (server and ML tags pinned in the `homesvr` repo, chart 0.13.4), newer than v2.4.0 where `GET /api/queues/{name}` appeared, so the API read should exist. There is no v4.0; the earlier "v4.0 or later" assumption is withdrawn.
- *Consumer-side actuators (`PauseIntake`, `KillInFlight`):* only if work is seen being cut off badly. They stay reported as "not executed".
- *Re-queue interrupted speakr summaries:* only if it is seen to happen, and after confirming speakr has a re-queue endpoint (not verified).
- *Tighten speakr demand counts:* only if the `/api/v1/stats` overcount visibly distorts a decision.

The `homesvr` repository is maintained by a separate agent: this project reads it only when a fact is needed and never writes to it. Deploying flowmanager (manifests, shadow-mode run, smoke test) is therefore done there, guided by `docs/kubernetes_setup.md`.

## Deferred beyond these milestones

These are supported by the design but intentionally left out of the plan above.

- **Demand-driven power:** switching the GPU node's power policy from manual to auto-wake, then auto-wake-and-sleep.
- **Per-service custom resources:** replacing the ConfigMap with resources that each service's manifests register themselves.
- **Cost-aware policy:** a predictive, cost-based strategy that weighs switch cost against waiting time, run side by side with the current policy on recorded snapshots before being enabled.
- **Lease-based admission:** services asking the scheduler for a lease before taking a job, instead of the scheduler inferring demand from outside.
- **Interactive leases with renewal and expiry,** and a model-routing proxy for interactive requests (dropped from M6).
- **SQL adapter:** a generic SQL queue source, no longer needed now that speakr's API covers its demand.

## Plan changes and follow-ups

Decisions made during implementation that change or extend the milestones above. Each item names the milestone that owns it. Do not drop items from this list until the owning milestone's exit criteria are checked against them.

### Decided during M2 (Oct 23-24, 2026)

- **Speakr failed transcriptions are invisible in M2 (owner: M7, user decision).** Verified against speakr's source: when a transcription job exhausts its retries (`JOB_MAX_RETRIES`, default 3, retried immediately), `job_queue.py` sets `status=FAILED` and stores the error in `recording.transcription` as `ERROR_JSON:{...}`, not in `error_message`. The v1 list API returns only `has_transcription`, so the original M2 scope item "count speakr transcriptions that failed with a connection error as pending demand" cannot be met from the list. M2 therefore sees speakr transcription demand only while jobs are PENDING, queued, or processing, which in a whisperX outage is only seconds. M7 must pick a detection method: per-recording detail fetch (`GET /api/v1/recordings/{id}`, match the ERROR_JSON error type, cache per recording id to stay inside the 120/min read limit), counting every FAILED recording in a window, or the SQL adapter against speakr's database (this makes the "SQL adapter no longer needed" note under *Deferred* wrong for this case). The `requeue_failed` recovery in M7 needs the same detection. **Superseded in M3 (Oct 24, 2026):** detection is done from the list after all (`status=failed`, `has_summary: false`, `updated_since` window of 15m), and automatic re-queueing, capped at 2 per recording, moved into M3; see *Decided during M3*.
- **Speakr queue counts come from `/api/v1/stats` (owner: M2, done).** The list API has no filter for `QUEUED`, which is the state a recording is in while it waits for transcription. Ready = `recordings.pending` + `queue.jobs_queued`; in-flight = `queue.jobs_processing`. These count all job types (summary, merge, stitch) for the token's user only, so transcription demand is a conservative overcount. M7 or later may tighten this if it distorts decisions.
- **Shadow output is stateless (owner: M2/M3).** Ticks start from a fresh sequencer state, so dwell, idle grace, drain, pause-intake and power-off never appear in M2 logs. Compare logs to human choices with that in mind. M3 is the first milestone where hysteresis can be judged.
- **Restate ingress is trusted-network only (owner: M3, user decision).** The `observe` handler accepts any valid-looking push for a configured source, so anyone who can reach the ingress could forge, for example, `pods: 0`. The cluster uses Istio mTLS, but mTLS authenticates and does not authorize. Before M3 (when a false zero can load a second model), add an Istio `AuthorizationPolicy` allowing only the flowmanager service account to call the Restate ingress, or move observer pushes in-process. Record the policy in the deploy manifests. **Settled in M3 P1:** `observe` is ingress-private, so nothing outside Restate can forge a push; the policy that still matters (the public handlers, and the service endpoint, which does not verify Restate) is described in `docs/kubernetes_setup.md`.
- **Kube dependency features (owner: done).** `kube` now uses `default-features = false` with `client`, `runtime`, `rustls-tls`, `aws-lc-rs` so only one rustls crypto provider is present. `futures` (0.3, std only) was approved for watch streams. `unsafe_code` is forbidden workspace-wide.

### Decided during M3 (Oct 24, 2026)

- **Speakr failed-transcription detection, and its automatic re-queue, pulled forward from M7 into M3 (owner: M3, user decision).** Detected from the list only, no per-recording fetch: `GET /api/v1/recordings?status=failed&per_page=100` with `updated_since=<now - 15m>`, counting items with `has_summary: false` (speakr stores a failed summary's error in `summary`, every other failure's in `transcription`) as `failed` `speakr-transcription` demand (a third demand bucket; see the re-queue entry below), as a second request of `speakr-pending`. **Corrected in P5:** this entry first counted them as ready demand and claimed the 15m window being below `age_threshold` (30m) kept a failure from reaching starvation priority; review showed ready failures with a class-level age rule could force model switches for work that only waits to be re-queued. Failed items now never age at all. A failure counts as whisperX demand until it is re-queued or 15m pass; a later edit of a FAILED recording (tags, title, inbox, highlight, share) bumps `updated_at` and restarts its window; permanent failures count until the window passes. Failed transcriptions are re-queued automatically (P5, below), at most twice per recording; after that the recording stays FAILED and ages out of the window. Missed: a reprocess-transcription failure on a recording that already has a summary (accepted). speakr load: 3 requests per minute against the 120/min read limit. Adapter: `where.equals` now compares JSON booleans and numbers as well as text (quote a scalar for text), and an item whose field is of another JSON type fails the poll instead of matching nothing.
- **Failed items are a third demand bucket, and speakr's failed transcriptions are re-queued automatically (owner: M3, P5, user decision).**
  - *Demand.* `counts_as: failed` (next to `ready` and `in_flight`) in an `http_json` source; `ObservedValue::Demand.failed` (default 0, so stored and pushed values still read) and `ClassWork.failed`. The example's failed-recordings request counts as `failed`. Failed items never contribute to the oldest ready item, so they can never be starved or force a switch by `age_threshold` (the claim that the 15m window kept them below it is withdrawn: nothing ages them). They do not make a class `busy` (so they neither power a host nor keep one up nor keep a model loaded), but they make the class's model *wanted* at the class's priority: the planner treats a model wanted only for failed items as new work (no age, last in ties of age), and ignores failed items for the model that is serving (they neither hold it nor make it the pick when it is released). A model loaded only for failed items is therefore released after the usual `min_dwell` and `idle_grace`. Known cost: if items cannot be re-queued (cap used) the model idles `idle_grace` and is released while they remain listed, and a lone failed-only class can bring it back until the items leave the 15m window.
  - *When.* The sequencer emits `RunRecovery` for a class with a recovery that needs its model, while the class is in the allowed set and the snapshot has fresh failed items, on every such tick; never for a class that is not allowed. The after-cut-off path no longer records such an action (the model was just withdrawn). Invariant 9 checks it independently.
  - *The action* `requeue_failed` lives in `sched-actuate` and is config-driven: list request (`url`, `items`, `id`, `where`, `since`, `max_items`), re-queue request (`method`, `url` with `{id}`, `expect` conditions on the answer), `auth` by env var, `max_attempts` (2), `window` (15m), `min_interval` (60s), `max_per_run` (5), `timeout` (10s). Validated at config load (unknown actions refused; a `RecoverySpec` typed in `sched-model`). It reuses `sched-observe`'s HTTP helpers; no new external dependency. The service-specific values are only in the config. `speakr-summarization` has no recovery (a failed summary is not re-queued). One token, scopes `read` + `process`, is used for polls and the re-queue (`POST /api/v1/recordings/{id}/transcribe`); it returns `{success, job_id, status: "QUEUED"}`, which the example requires via `expect`.
  - *Where it runs.* In a separate Restate virtual object, `Recovery` (key: class id), not in the `Scheduler`: a `Scheduler` handler holds the exclusive lock and HTTP there would queue ticks and lease requests behind a slow service. The tick sends it a one-way request after publishing the allowed set; the object has its own lock, so a hung action cannot delay a tick. Journaled steps (gate, list, per-item allowed check, per-item request) mean a replay cannot re-send; every request has a timeout.
  - *The cap is durable.* Attempts per item id are in the `Recovery` object's state, key `recovery_attempts`, versioned `{"version":1,"data":{last_run_at, attempts:{id:{count,last_at}}}}`. The attempt is recorded and made durable (a state write followed by a journaled barrier step) before the request is sent, so a crash between recording and sending cannot allow a third attempt. Residual: a crash after the request went out but before its result was journaled makes Restate repeat that one request for the same recorded attempt (journaled steps are at least once). Records are kept for `retention` (default 24h, at least `window`) after the last attempt whether or not the item is listed, then forgotten (review round: pruning by the list window let a recording that left and re-entered the list get fresh attempts). A recording edited after the retention may get a fresh two (deliberate limit). `Recovery.run` is ingress-private; metrics label only configured classes. A full page of failed recordings no longer fails the poll (failed requests only): it counts the items on the page that pass the `where` filter, as "at least N" (P4 fix: it first counted `max_items`, so a page of 100 failed summaries would have counted as 100 failed transcriptions); a page entirely filled with non-matching failures hides transcription failures beyond it. Known flapping while spent items stay listed (release after `min_dwell`+`idle_grace`, re-allowed, until the `since` window passes) is documented in the README.
  - *Reporting.* `RunRecovery` is reported as carried out; `KillInFlight`, `PauseIntake` and power steps stay "not executed". Metrics `sched_recovery_runs_total` and `sched_recovery_requeues_total` distinguish attempted, queued, failed, skipped (cap), skipped (not allowed), deferred.
  - *Not done / accepted.* The list request is written twice in the example config (the source's and the recovery's); keep them in step. A reprocess-transcription failure on a recording that already has a summary is still missed.
- **Prometheus observer pulled forward (owner: M3).** The `prometheus` kind now has an observer supplying reachability: one instant query per resync, exactly one series, `1` up and `0` down; HTTP or Prometheus errors, a non-vector result, no series, several series or any other value are source errors, never "down". Params: `url`, `query`, `resource`, `timeout`, optional `auth`, `reachability_confirmations` (debounce, default 3, as for the kube watch). `-0` and `-1` are refused, `1.0`/`0.0` accepted. **Superseded for basestar (Oct 24, 2026):** `basestar-probe` first used it, but no blackbox exporter probes basestar; basestar now uses the TCP probe below and the `prometheus` kind is kept as a supported spare for other sources (its observer, tests and docs stay).
- **basestar reachability from a TCP connect probe, as power.py checks it (owner: M3, user decision).** The user does not run a blackbox exporter for basestar, and power.py decides basestar is up by a plain TCP connect to `HOST:PORT` (default 2049, NFS) with a short timeout, treating a port that does not answer as down. New source kind `tcp_probe`, reachability only, for one configured resource: each resync one connect to `host:port` (the connection is closed at once, nothing is sent). Connected is up; refused, no answer within `timeout`, or "no route to host" (`EHOSTUNREACH`, what Linux reports after about 3s, or sooner while an earlier ARP lookup is pending, for a same-subnet address that does not answer ARP, i.e. a powered-off host) is down (Orchestrator decision, fix round 1: observed in the container, a dead same-subnet address gives `EHOSTUNREACH` after ~3.06s, so mapping it to an error would leave a powered-off basestar stale). A failed or slow name lookup, no address, "network unreachable" (no route at all), an unusable address or any other local error is a source error, never "down". Debounced with `reachability_confirmations` (default 3), failed reads are not readings. One probe takes at most `timeout`: lookup and connect share one deadline. Several resolved addresses are probed at once within it: up if any connects, down only if every address answered down, otherwise a source error. Params: `host` (name or IP address), `port`, `resource` (must exist), `timeout` (default 2s, 100ms..60s, not above `resync`), `reachability_confirmations`. `basestar-probe` is `tcp_probe` to `basestar:2049`, timeout 2s. It shows that the port accepts connections, not that the NFS export works. The `prometheus` kind stays as a spare (see above).
- **immich reads the queue API (owner: M3; immich-ml scheduling stays M7, now a backlog item).** `GET /api/jobs` is deprecated since immich v2.4.0; `immich-queues` reads `GET /api/queues/{smartSearch,faceDetection,ocr}` (alpha since v2.4.0, not in v2.3.1; the deployment runs v3.3.3 (read from the homesvr manifests, Oct 27, 2026; no v4.0 exists); admin key with `queue.read`, sent as `x-api-key` from `IMMICH_API_KEY`), `statistics.waiting` + `statistics.delayed` as ready and `statistics.active` as in-flight, summed. A paused queue counts as zero (user decision): in the versions this was written against a paused queue reports its jobs under `waiting`, so each request carries the new generic `when: { field: /isPaused, equals: false }` response condition (a response that fails it contributes zero; a missing or non-boolean field fails the poll).
- **Stateful, durable core (owner: M3, done in P1).** The `Scheduler` object keeps the sequencer state, which sources have ever reported, and the manual model leases in its Restate state; each tick decides inside a journaled step and publishes the allowed set in process (a `watch` channel of `Option<PublishedAllowed>` for the KEDA scaler) only after that step returns. `observe` is ingress-private, which also settles the trusted-ingress item of M2 for forged pushes. Manual model leases have an ingress API (acquire, release, list).
- **Power control is per resource, `manual` by default (owner: M3; `managed` is M4, user decision).** `power.control: manual | managed`. Under `manual` the scheduler never emits `PowerOn`/`PowerOff`, never takes responsibility for a host's power, and the power phase follows observed reachability; a manual model lease on a host that is off waits (`HostNotUp`) for a person. Persisted transitional phases from managed control converge to the observed one. Motivation: with no power actuator, a released manual LLM lease led to an unexecuted `PowerOff` and the GPU stayed "shutting down" with nothing allowed. M4 switches hosts to `managed` together with the power actuators; the managed machine and its tests are kept for it.
- **Demand that can never be observed counts as no demand (owner: M3, user decision).** A class whose source has no observer in this build (its kind has none, or an observable kind is configured without params) and that has never reported (per the persisted reported-sources set) is not busy, for the planner and the sequencer, host holds included. `observe` is ingress-private, so such demand can never arrive; as unknown, the example's `interactive-llm` (`llm-sessions`, a session source) kept the LLM loaded forever. A source that has reported before and goes silent stays unknown (busy). Passed to the pure core as data (`Snapshot::unobservable`). The `schedule` kind was removed in M4 (scheduled jobs are not demand sources; they take a shared hold instead). The session kind no longer has a planned observer (M6 shrank to the manual lease).
- **Scope reset: queue-only switching; Kubernetes enforces GPU exclusivity; gate classes on host readiness (owner: M3, done in P6, user decision).**
  - *Kubernetes enforces GPU exclusivity.* Every GPU workload requests `nvidia.com/gpu: 1`, the device plugin exposes one GPU on cuda-central (no time-slicing), and the GPU node is tainted. This is now a deployment requirement (architecture invariant 2). flowmanager gates no decision on pod state: it decides from queues, leases and policy only, and publishes at most one model per exclusive resource. A switch withdraws the old model and allows the new one in the same tick; the new pod stays pending in Kubernetes until the old one has released the GPU. Pod counts remain observations (and metrics) for information only; a config no longer needs a pods source.
  - *State machine.* The mode of an exclusive resource is idle or serving (possibly winding down); `loading` and `draining` are gone, and with them the wait reasons `loading`, `draining` and `other_model_present`. A model is serving from the tick it is allowed, so `min_dwell` counts from that tick and includes load time. Wind-down keeps the queue-based rules (in-flight counts, `min_dwell`, `max_dwell`, `age_threshold`, forced manual leases and reclaims with their timeouts, per-class `kill_timeout`); they decide when to switch, and the wait for in-flight work is bounded by a timeout whether forced or not (see *Bounded wind-down* below). Allowing a model (alone or in a switch) needs a fresh "up" reading of its host (`stale_observation` now means reachability only); withdrawing needs nothing. `RunRecovery` runs in the tick the model is withdrawn. Power-off no longer looks at pods (it happens only with no model allowed).
  - *Persisted state.* `scheduler_state` keeps version 1: `loading` written by the previous build reads as serving since the same instant, `draining` as idle (any pending recovery then runs). Everything this build writes the previous build can read, so neither direction is an error tick.
  - *Removed models.* A model removed from the config while allowed leaves the allowed set at the next tick after reload, with no dwell, grace or wind-down; persisted state naming an unconfigured model does not block the resource (this replaces the stall described in the next item).
  - *Gate classes.* A requirement on an exclusive resource without a model is valid and means "that host is up". Such a class must have no demand source (refused at load otherwise) and never influences model choice. The example config adds `paperless-gpt` (cuda-central up and basestar-nfs up). Consumers (paperless-gpt, speakr, immich) are not gated for GPU contention: switching a model away mid-job is safe for all of them (paperless-gpt reprocesses an unfinished document, speakr marks the job failed and it is re-queued, immich falls back to its CPU replica).
  - *Reporting.* `PauseIntake` only removes a demand class from the allowed set, which no consumer scales on, so it is listed in `not_executed` (nothing stops the consumer taking new work, so in-flight counts may stay up). `KillInFlight` is listed too, with a note that it has no actuator: the work ends because the model is withdrawn.
  - *Bounded wind-down (P6 fix round).* Review found that an unforced wind-down had no timeout and, with `PauseIntake` stopping nobody, a continuously fed queue held the GPU for ever (reproduced in a 48h simulation and live: whisperx with a job always processing; real case: immich-ml's `statistics.active` during a library import). Decided: every wind-down has a timeout, counted from its start: the class's `kill_timeout`, else `reclaim_timeout` (reclaim) or `drain_timeout`. A cause change restarts the clock only when it flips between reclaim and not-reclaim; a manual lease coming or going keeps it. Preemptibility `none` with busy work still blocks the switch (`not_preemptible`) without a timeout, the only unbounded case. End-to-end bound, checked against the planner (`fifo.rs`, `target_for`): intent leaves a busy serving model at the first tick with served time > `max_dwell` (or once another queue's oldest ready item is older than `age_threshold`; never before `min_dwell`), only if some other model has runnable ready work and no busy class is `none` or unknown; the switch completes at most the timeout later, so a model allowed at `t0` is replaced by `t0 + max_dwell + drain_timeout` plus a tick period (2h10m in the example). Example config: paperless-ocr and paperless-tagging are `kill` (paperless-gpt reprocesses unfinished documents); speakr-summarization stays `pause_intake` and an interrupted summary is not re-queued automatically (the planned speakr recovery covers failed transcriptions only). Rolling the binary back needs the config rolled back too (the old build refuses gate classes and a config without a pods source). A tick in which a manual model lease pins a model lists the kind `pinned` and never `idle`. **Caveats found in P6 review (decision: document, do not change):** the end-to-end bound holds only while the planner's intent is stable. If the intent flickers back to the serving model (the waiting queue reading `ready = 0` for one tick every few minutes, or the serving class's demand going stale for one tick every few minutes) the wind-down is dropped (`wind_down: None` in `exclusive.rs` `serving()`) and its clock restarts, which can postpone the switch indefinitely (reproduced in simulation: a one-tick blip every 9 minutes never switched in 6 hours). A class's `kill_timeout` shorter than another blocking class's timeout does not end the wind-down early: each class is cut off at its own timeout, but the model is withdrawn only when no class of it still blocks, so the effective bound is the maximum over the blocking classes' timeouts. A reclaim that starts and ends in the middle of a wind-down restarts the clock twice (a 10 minute timeout took 16 minutes). Related defect fixed in P4: `idle_since` was not updated on the wind-down path, so a value left by a blip made a busy model look idle and `idle_grace` could be satisfied by accumulated blips (a switch at minute 54 in a 9 minute blip scenario); it is now kept in step with the queue on every path.
- **A model removed from the config while loaded (owner: later M3 phase, user decision; done in P6, see the scope reset above).** GPU exclusivity is enforced by Kubernetes itself (`nvidia.com/gpu: 1`, no time-slicing), so a later phase removes pod-count gating from the core. The planned "retain a removed model's mapping until its pods are at zero" change was cancelled. Until then (checked in P1 fix round 1 with a throwaway multi-tick run: whisperx serving, its model, class and sources removed, OCR waiting): the removed model stays in the published allowed set until the planner releases it after `idle_grace` (10m), then it is drained and the sequencer waits forever (`stale_observation`) on a pod count the cache no longer accepts, so the waiting OCR work is never scheduled. Recovery today: put the model back, or discard `scheduler_state` once its pods are gone.
- **Persisted state is versioned (owner: M3, done in P1).** `scheduler_state` and `lease_book` are stored as `{"version": N, "data": ...}`. A document that cannot be decoded or has another version (e.g. after a rollback) is not reset and does not fail the invocation (no retry loop blocking the exclusive handlers): the tick reports an error (report, error log, `sched_persisted_state_errors_total{key}`) and publishes nothing; the lease handlers keep working where they can. Recovery: the `discard_state` handler, or the Restate CLI (README). Bump a document's version whenever its shape changes incompatibly.
- **KEDA external scaler (owner: M3, done in P3; user decisions: 0/1 replicas, `model`/`class` metadata, retire the legacy gating).** `sched-keda` serves KEDA's `externalscaler.ExternalScaler` (proto vendored unmodified from KEDA v2.21.0, commit 626ded5, Apache-2.0, provenance in `crates/sched-keda/proto/NOTICE`) with tonic 0.14.6 / prost 0.14.4 (plus `tonic-prost`, and `tonic-prost-build` at build time; needs `protoc`, listed in `mise.toml`). The binary serves it on `--keda-listen` / `SCHED_KEDA_LISTEN` (default `0.0.0.0:9095`), plaintext gRPC on its own task (Istio provides mTLS), as a lookup over the published allowed set; ticks and scaler calls never wait on each other. Metadata: exactly one of `model: <id>` or `class: <id>`, the id known to the active config; KEDA's own trigger keys (`scalerAddress`, `enableTLS`, `unsafeSsl`), which KEDA passes on, are ignored; anything else (none, both, another key, an empty value, an unknown id) is `InvalidArgument`, never a silent 0. `IsActive` is membership; `GetMetricSpec` one metric `flowmanager-{model,class}-<id>` with target 1; `GetMetrics` 1 or 0 (int and float); `StreamIsActive` sends at once and then only on that object's own change, and ends with the error if the answer becomes one; `StreamMetricSpec` is `Unimplemented` (KEDA falls back to pull). Before this process's first tick every call is `Unavailable` (KEDA v2.21 keeps the replica count on scaler errors when there is no `fallback`), and so is every call once the allowed-set sender is dropped (the process is stopping; the last answer could no longer change). Ids are checked against the config as it is now: an added id is answered from the allowed set (inactive until a tick allows it); a removed id is refused even while it is still published, so KEDA freezes that object's replica count (a removed model that was running keeps running until its ScaledObject is fixed or deleted; see the item on removed models above). ScaledObjects: `minReplicaCount: 0`, `maxReplicaCount: 1`, short `pollingInterval`/`cooldownPeriod`, no `fallback`, the scaler as the only trigger (README). The legacy `paused-replicas` gating (root crate `KedaGroup`/`KedaCatalog`, its drain wait and `--drain-timeout-secs`, and the `GROUPS`/`DRAIN`/`EXCLUSIVE_ROLES` server keys, now ignored) is removed; `kubernetes-requirements.md` marks it retired and says how to migrate a gated ScaledObject (the `paused-replicas` annotation must be removed, or KEDA stays paused). Not yet done: the ScaledObjects in the deploy repo, and a run against a real KEDA (`docs/kubernetes_setup.md` is the guide for writing them).
- **PowerOn/PowerOff timeouts (owner: M4, done).** PoweringOn and ShuttingDown time out into a visible `Failed` phase with an alert; nothing is retried automatically. Added with them in M4: `min_off` (a per-resource minimum off time after a confirmed shutdown, default 0), the NFS mount-check veto with `mounts_timeout`, and `resume`.
- **A host found running is adopted (owner: M4 host power, user decision; changes the earlier "found running is never powered off").** For a shared host with `power.control: managed`, a host observed up that flowmanager did not power on (no state, seen `off` before, or a failed power-on cleared by a reading) counts as held by the user: the tick mints the existing `ManualHost` lease for it (id `adopted-host-<resource>`), before the planner runs, so the sequencer stays pure and the tick is deterministic from the previous state and the readings. Not adopted: a host flowmanager powered on (`powering_on` seen up: a job's hold, a lease through the API), a host already `on` (a restart with persisted state), anything under `control: manual`. An adopted lease is dropped when a fresh reading shows the host down, so a host switched off by hand is not woken by a lease nobody asked for. After `resume` the host is found running again and is adopted. A failed power-on cleared by a reading is adopted too (the sequencer already treated it as found running). The choice of an id prefix over a new lease kind keeps `LeaseKind` and the stored lease book unchanged.
- **Drain on release (owner: M4 host power, user decision).** `release_host_lease` takes an optional `drain` of `graceful` or `immediate`, kept in the host's `ResourceState` (`drain: {mode, since, scaled_down}`, absent when unset, so stored states read and write as before and the state version is unchanged). It ignores queued and in-flight work for the shutdown decision (never leases: a job's hold is waited for, `wait ... drain_held`), takes the classes that need the host out of the allowed set (the existing host gate in `class_allowed`, which KEDA already follows) at once or, for `graceful`, when nothing is in flight or `policy.drain_timeout` has passed, then shuts down through the usual mount veto. Simplest choices: one timeout (`drain_timeout`, not a class's `kill_timeout`); an unknown in-flight reading waits for the timeout; a drain request marks the host managed and clears a stopped mount veto, as a manual request does; a new manual lease cancels the drain. Known limit: a class that may change power and still has queued work wakes the host again once it is off. Review round 2: a host flowmanager powered on that blips down and back stays `managed` and is not adopted (only `off` with the flag clear is: after our shutdown, found down, or an adopted lease dropped on a down reading, which clears it); the Home Assistant reply shows the handler's answer, never a stale report drain. Review round: the switch-off calls a new `drain_host` handler, which needs no lease and changes a drain under way in place (no lease round trip, no dependence on the last report); a host stored as `on` and unmanaged is adopted unless a mount veto, a drain or a job hold explains it (the state of the live NFS host after the upgrade); a managed shared host always has a `mounts` source, so the `idle_grace` wait first planned for a host without one was removed; rolling back while a drain is stored makes the older build refuse the state until it clears.
- **Idle drain: the consumers go down before an idle shared host does (owner: M4 host power, user decision: option B).** Consumers of a shared host run while it is up, whoever woke it, and the end of the last hold scales them down before the shutdown, so their pods do not keep mounting a host about to go and every backup's wake does not end in a `mounts_timeout` stop. Built as `Drain.origin` (`requested` default, absent from the stored form; `idle`): when a managed shared host reaches today's `power_off` point (nothing holds it, no unknown demand, `idle_grace` over) the sequencer records an immediate idle drain and runs the existing drain shutdown in the same tick (consumers leave the allowed set, then the mount veto and `mounts_timeout`, then `PowerOff`; so the number of ticks and the mount wait's start are unchanged). Choices: any hold cancels an idle drain (lease of any kind, a job's hold, busy demand) and restarts the idle clock; unknown demand starts none and keeps one set without a shutdown; a Stopped mount veto clears an idle drain (the host is then unmanaged, so nothing restarts it); a person's `drain_host` replaces an idle drain with a requested one (start and scale-down kept); exclusive hosts and `control: manual` are unchanged. Cost: a stored idle drain is a field an older build cannot decode and appears at every idle shutdown (a requested drain is stored as before), documented next to the other rollback caveat. Not covered: the pod count read at the moment of the scale-down may predate it, but a reading above zero is what the veto waits on, so only a reading that says zero while pods mount could let the shutdown run early: one older than `host_reading_stale_after`, or a fresh zero that predates a pod created since the last watch event (a Pending pod counts from its creation). The shutdown before this branch had the same window.

### Scope reset during M3 (Oct 26, 2026)

Decisions by the user while M3 was being built. **Decisions by the user**

- **Queue-only switching.** flowmanager decides which model runs from queues, leases and policy only, never from pod state.
- **Kubernetes enforces GPU exclusivity.** Every GPU workload requests `nvidia.com/gpu: 1`, the device plugin exposes one GPU, the GPU node is tainted. flowmanager publishes at most one model per exclusive resource.
- **Consumers always run.** speakr, paperless-ngx and immich-server are not scaled by flowmanager (their queues must stay readable); only the model workloads scale, and a consumer that may run only while hosts are up (paperless-gpt) scales on a gate class.
- **Gate classes** on host readiness.
- **The Prometheus observer stays as a spare kind** while basestar's reachability comes from the TCP probe (`tcp_probe`), the same check `power.py` makes.
- **M4 becomes "scheduled jobs and power".** flowmanager owns the schedules of arbitrary Kubernetes Jobs (for example "doing a backup"); a job declares what it needs (NFS, possibly a GPU mode later). The existing backup CronJob's `jobTemplate` is the template; the CronJob is `suspend: true`, so flowmanager triggers Jobs and the CronJob controller does not. Backup jobs run in parallel, verification happens in their init-containers, and on failure flowmanager alerts and releases. flowmanager will own the NFS and GPU power transitions, reproducing `power.py`'s `low` state (NFS up, GPU down); it gates NFS dependents (scale to zero while basestar is off), checks that no pod mounts NFS before shutting basestar down, and does the same bounded drain before a GPU shutdown. A manual NFS lease brings up basestar **and** the consumers so queues become visible; a GPU lease enables scheduling. The `idle` group of `power.py` is ignored for now.
- **Open M4 questions:** the catch-up policy for missed scheduled runs; the overlap policy; server definitions in labelled ConfigMaps versus in the config; timeouts and alerts for `ShuttingDown` and `PoweringOn`.
- **M5 (webhooks) was deferred** to a separate conversation, then decided and built (see M5): a webhook that reports state, not one that acts.
- **M6 shrinks** to Open WebUI tied to a manual model lease with a manual release; **M7 shrinks** accordingly.

**Consequences and proposals (not yet confirmed by the user)**

These are inferences made while rewriting the plan; confirm or change them.

- The `session` source kind and the interactive-session marker go away with the reduced M6; interactive TTL leases and the model-routing proxy move to *Deferred*.
- The `schedule` source kind is replaced by the scheduled-jobs design in M4.
- Proposed overlap-policy default for scheduled jobs: skip a run while the previous one is still going.
- Proposed policies for scheduled jobs, raised when asking what happens if basestar cannot come up for a backup window and the next window arrives (not yet confirmed):
  - *Overlap, per job:* at most one instance of a given job at any time. A run that comes due while the previous instance of the same job is pending or running is skipped and logged, never run in parallel or queued behind it. This is separate from distinct jobs running in parallel, which stays as written for M4.
  - *Catch-up:* a run missed because flowmanager or the cluster was down, or because its needs (NFS) could not be brought up, is run at most once, late, and only if it has not been superseded by the next scheduled time. If the next window arrives first, the missed one is dropped and the skip is logged and alerted, so a long outage never produces a burst of back-to-back backups.
  - *Retry:* each job declares a retry limit (proposed default 1 retry after a failure, with a backoff). After the limit the job is marked failed, an alert is raised and what it held is released; the next scheduled time starts a fresh attempt. A job whose needs never came up counts as a missed run (above), not as a failed attempt.
  - Neither exists in M3: the `schedule` source kind has no observer, so the example's `backup` class has no demand and flowmanager starts no backup yet.

### Power-model refactor (Oct 30, 2026)

The code behaves as `power-model.md` describes. Phases, each run through the three-role process (on `refactor/power-model`; phases 1 to 5 done, phase 6 built and awaiting review):

2. **State types** — done: `Shutdown{cause, stage}`, `off_since`; drop `drain`, `mounts_veto`, `shutdown_confirmed_at` (`managed` became `ours` on `Off` and `On` in 4b); renumber the invariants in code.

4. **Vocabulary and adoption** — done (4a vocabulary and lockout, 4b ownership): `off` / `off-now` on both host kinds; reclaim renamed lockout on any managed host; adoption in the sequencer with a typed origin; no `jobs_off` coupling.

Breaking changes to logs, reason strings, metrics and state are accepted (D4, D5); each phase reports them for the homesvr hand-off (`power-model.md` section 5).
